## 2026-11-10 — Making the game work beneath /Morkahja/

With the address settled, I asked for the repository side of the move to be implemented and tested without touching production until I approve a cutover. The frontend had been built on the assumption that it lived at a domain root. Around forty components named their artwork, music and sound effects with paths like `/UI/…` and `/game/…`, and the server also sends a few such paths for feed and achievement icons. AI-assisted work added a single base-aware asset helper and routed every one of those paths through it, rather than exposing the game's asset folders at the website root. It also set the Vite base, made the PWA manifest resolve beneath `/Morkahja/`, and fixed a social-preview image that had silently pointed to a removed file.

Testing behind a real Nginx proxy surfaced a less visible problem. Express did not trust the proxy's forwarded address, so every player would have appeared as `127.0.0.1` and shared one sign-in and heartbeat rate limit. A couple of dozen people online at once would have started logging each other out. The backend now trusts forwarded addresses only from a same-host proxy.

A public look at the domain changed the picture. The apex `babuni.dev` still points to the registrar's parking page and has no HTTPS certificate, while my website actually runs on `www.babuni.dev`. So the requested URL needs a DNS and certificate decision first; nothing in DNS was changed. Same-origin hosting also means any script on the website could read a player's identity key from browser storage, which is now documented as a security consideration rather than designed away.

**Babuni's direction:** Implement and verify the repository changes for `https://babuni.dev/Morkahja/`; no production DNS, Nginx, services, database or Stripe changes without explicit approval. **AI contribution:** Asset/base-path implementation, the proxy-trust fix, an Nginx template, tests, public infrastructure discovery and the updated deployment plan. **Verification:** `npm run release:check` passed locally against a disposable PostgreSQL container. ## 2026-11-10 — One copy of the game content

The encounter, solution, expansion, frame and portrait JSON started life as a Firebase export and had since been copied three times: once for the server, once built into the client, and once in the client's public folder, where my admin tool saved its edits. Nothing kept those copies in sync, and a content change only reached players after a client rebuild. I asked whether the content could move into the database so the game could be changed live. After reviewing the options, I chose a first step: make the server the only owner of the content and have the client fetch it, leaving a database move for when I edit on the live server.

**Babuni's direction:** One source for game content; content edits should reach players without a rebuild; keep the database move as a later step. **AI implementation:** `server/game` is the only copy. The server serves it at `GET /game-data/content` with an ETag, reloads a file when it changes on disk (keeping the last good copy if an edit is invalid), and writes admin saves atomically. The client loads the content during the loading screen; the duplicate client copies were removed.
