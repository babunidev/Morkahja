## 2026-11-12 — Unreleased: line frame around the encounter, with a wait timer

- **Change (Babuni's design):** the long bar graphics around the encounter picture are replaced by thin gold lines drawn in SVG: from the picture outward a 2 px line, a 2 px line with random gaps, a 1 px line, a small gap and an outer line. Small triangles fill the picture's corners and every line cuts its corners at the same angle, so the frame is octagonal (`DecorativeEdgeFrame.tsx`, geometry in `encounterFrameGeometry.ts`). The gaps are random but seeded, so they stay the same between renders. The Inventory, Skillbook and Lore overlays use the same frame. On narrow screens the picture is 22 px narrower so the frame fits on screen.
- **New: the bottom line is a timer (Babuni's direction).** While the player has to wait for an animation, a bright line fades in on the bottom edge and shrinks from both ends toward the element being waited for, ending when the game is ready for the next action (`client/src/ui/game/frameTimer.ts`). It covers: the actions appearing at the start of an encounter and solutions flying into their slots (toward the dice), the dice roll, using a solution (toward that solution), the used solution's flight and rewards arriving (toward the rewards), losses arriving (toward the losses), the wait until rewards and losses can be collected (toward them) and the Continue arrow appearing. When two waits overlap, the line follows the one that ends last.
- **Verification:** client typecheck, tests (24, including new geometry and timer tests) and production build passed. In headless Chrome at 1400 × 900 and 412 × 915, the frame was screenshotted, and the timer was traced every 200 ms through whole rounds: dice roll (1.35 s), reward arrival (about 1 s), losses (about 1 s), the wait until collecting (about 3 s), and the next encounter's actions appearing; each shrank toward its target and ended on time. **Not deployed.**

## 2026-11-12 — Unreleased: one tooltip style across the game screen

- **Change (Babuni's direction):** the inventory tooltip style now applies across the game screen through one shared component (`client/src/ui/game/GameTooltip.tsx`): solutions (the dice in the middle slot gets the centred variant), rewards and losses in the result, a new "Continue to the next encounter" tooltip on the Continue arrow, short descriptions for Get help ("Call nearby adventurers to help!"), Inventory ("The items you carry"), Skillbook and Lore, and the avatar's name and level as a preview. Every game tooltip opens toward the middle of its bounds (the encounter picture; the whole game screen for the menu and avatar), is anchored by a corner or edge with the gold marker, appears after a 350 ms hover delay (touch keeps its long press) and fades in and out. The Inventory and Skillbook tooltips got the same hover delay.
- **Fix: a long press also pressed the button on touch screens.** Releasing a long press fires `pointerup` and `pointerleave` before `click`, and `pointerleave` cleared the "long press" flag, so the click went through: holding a solution to read its tooltip would use it, and holding Lore, Call for help or the avatar opened or triggered them. The flag now survives the release and expires after a second (`useTooltipReveal.ts`); long presses on rewards and losses no longer collect them.
- **Fix: scroll bars inside tooltips (reported by Babuni).** Solution, inventory and party-member tooltips had a height cap with `overflow: auto`; the gold marker sits just outside the frame, so even the short dice tooltip showed scroll bars. The cap is gone and the tooltips size to their text (`SolutionBlock.tsx`, `SolutionGridTooltipPanel.tsx`, `encounterTooltip.tsx`).
- **Verification:** client tests (19) and production build passed. In headless Chrome at 412 × 915 with touch long presses: the dice and a middle-slot reward showed centred tooltips, the menu and avatar tooltips stayed inside the game screen, all with markers, and after the long presses the Lore panel and avatar details stayed closed and help was not called. Headless Chrome cannot emulate a mouse hover, so the desktop hover path (delay before showing) was not observed by AI. **Not deployed.**

## 2026-11-11 — Deployed: level-up event no longer plays twice; lore gem flies to the avatar (`main` at `e78cde2f`, PR #26)

- **Fix: a level-up event could be played twice, with its rewards granted twice.** Choosing in a system event and then leaving a solo adventure, or only going away (page reload, switching tab or window), committed the event on the leave path (`commitParticipantOutcomeOnLeave`) but left the room on it, so the player could play the same event again on return. That path also added the room XP bonus to the level-up event. When the player stays listed in the room, the leave and away paths now defer the system event, and `resolveSystemEventLeftByActor` resolves it through the same routine as Continue, once, and moves the room on (`server/src/services/roomService.ts`). Found from Babuni's report; the event log showed it for Babuni's local avatar and an early bot. New test `server/src/services/systemEventLeaveOnce.test.ts` (leave and away) fails on the old code and passes now.
- **Lore gem (Babuni's direction):** a collected lore gem flies onto the avatar portrait instead of into the inventory, since gems belong to the player, not the inventory.

## 2026-11-11 — Game screen layout from the standalone version (branch `feat/standalone-layout`, merged as PR #24)

- **Game screen:** three zones on one fixed 9:16 design canvas (390 × 693) scaled as a unit, instead of the 61.8 / 38.2 split: the encounter picture in a decorative edge frame (58%), a party strip (30%) and an action menu (12%) with Get help, Inventory, Lore and Skillbook. Ported from Babuni's standalone desktop version (August–September 2026), which was copied from web commit `77062a42`.
- **Details:** the encounter title appears when hovering the picture instead of in a header strip; Lore, Inventory and Skillbook panels open inside the frame with a title; avatar details open as a card beside the party slot; essences show as up to five "lives" under the avatar; solution icons fly from the Inventory or Skillbook button into their slots, and the button gives a small kick; the same sound effect no longer restarts while still playing; avatar tooltips show title and name on separate lines.
- **Result presentation (Babuni's direction, 2026-11-11):** the result shows only rewards, losses and Continue; the outcome word (Fate, Prosperity, …), the roll number and the dice icon are gone, since the roll already shows below. As the result appears, the used solution flies from its slot into the middle of the encounter picture and shrinks to nothing. Losses arrive from where they were kept, an essence from the middle of the avatar and an item or skill from its Inventory or Skillbook button, to their place in the loss row; on Continue they still rise and fade away, and rewards still fly into the inventory (`client/src/ui/game/rewardFlyAnimation.ts`, `ResultBlock.tsx`).
- **Leaner result (Babuni's direction):** the result's background bar is gone. The result now uses the solution bar's place and five-column grid, which is hidden while a result shows: rewards (and an earned lore gem) sit in the A–D solution slots at solution size, Continue sits in the middle where the dice slot is, and losses float just above. More than four rewards, as on some level-ups, continue in a row above the bar.
- **Rewards grow out of the encounter (Babuni's direction):** rewards start as a point in the middle of the encounter picture and grow while travelling to their slots, the reverse of a used solution; after a used solution they emerge just as it vanishes. Continue appears once rewards and losses have landed, and if the animation is interrupted the rewards simply show.
- **Collect to continue (D-011):** when a result holds rewards or losses for the player, there is no Continue arrow. Each item is tapped to collect it, a reward flying into the Inventory or Skillbook and a loss rising away, and collecting the last one continues the round exactly as Continue did (if continuing fails, the items return). With nothing to collect, and when watching another player's turn, the Continue arrow appears as before.
- **Result slot order and ready wobble (Babuni's direction):** rewards, an earned lore gem and then losses share the solution bar's five places, filled middle first: 3, 2, 4, 1, 5 (2, 4, 1, 5 when the Continue arrow holds the middle); more than five continue in a row above. When they become collectable, each gives the solutions' short "ready" wobble once, slot by slot.
- **Fix: endless render loop on the game screen (crashed a Chrome tab).** `PartyZone` stored each slot's "details open" flag in a new object even when nothing changed, and the party slot and avatar panel reported that flag from an effect that re-ran whenever they received a new inline callback; together that re-rendered forever ("Maximum update depth exceeded", about 527,000 times between 01:39 and 04:01 on 2026-11-11), until Chrome stopped the tab (renderer SIGILL). The setter now keeps the same object when unchanged, and the children report only when the flag itself changes. The loop came with the layout port from the standalone version.
- **Fix: the spending animation replayed when collecting.** Continuing re-renders the result with the server's final values (and can switch between result variants), which reset the component's memory of what had played. Spending, loss-arrival and reward-emergence animations are now remembered per encounter outside the component (`claimAnimationOnce` in `rewardFlyAnimation.ts`) and play once. A remaining case, the spending animation at the start of the next encounter with that encounter's solution image, came from the result briefly holding the previous roll and slot while the encounter id was already the new one; result animations are now tied to the action the player actually committed in that encounter (`recordCommittedAction`, recorded by the solution bar at commit).
- **Smoother landings:** every flight that ends on a real object (solutions into slots, rewards out of the encounter, losses to the row) now arrives, fades its glow while the real item fades in underneath, then fades out over it; items are revealed one by one as their own flyer lands instead of all at once.
- **Smoother transitions:** solutions landing in their slots no longer flicker; the flyer stays fully visible while the slot icon fades in underneath, then is removed. A used solution lifts off gently, and its slot icon hides the moment the flyer takes over, so only one icon shows. All flights now use the icons' on-screen size, since the game stage is scaled and the flyers are not, which removes a size jump on landing.
- **Bot adventurers on the live server (D-012):** the test bots became permanent residents with names in the world's style: **Varrokh** (Rokur Warrior, always adventuring), **Sylvaen** (Verdani Mage, waits and answers Call for help) and **Thalyss** (Aevis Rogue, plays seven rounds, rests five minutes and helps meanwhile). Their avatars take the portrait's own name, like the creation screen's default. The script is now `server/scripts/bot-adventurers.ts`; it still refuses `NODE_ENV=production` unless `BOT_ALLOW_PRODUCTION=1` is set, and `ecosystem.config.cjs` runs it next to the API as `morkahja-bots` with only that opt-in and the local API address (no database or `.env` secrets). `MORKAHJA_BOTS=0` in `.env` leaves them out.
- **Action menu order (Babuni's direction):** Get help, Inventory, Skillbook, Lore, from left to right.
- **Kept from the web version, not taken from the standalone:** Call for help (now in the action menu), the Friends-only slot setting, lore gem rewards and the waiting star, multiplayer witness and kick logic, reward visibility rules, and all server, payment and recovery features. Removed the now-unused `PlayerHub`, `EncounterFooter` and `EncounterHeaderSeam`.
- **Fix: Call for help skipped players with a paused solo adventure.** Leaving a solo adventure only pauses its room, and the player stays listed as its participant, so help invitations treated them as busy for good. This also stranded helpers: when a caller left, the helper was alone and its own leave only paused that room. A player now counts as busy only when their presence points at the room or the room is a party with someone else engaged (`isPlayerBusyInRoom` in `server/src/services/roomService.ts`). New test `server/src/services/helpInviteAvailability.test.ts` fails on the old rule and passes on the new one. Found while Babuni's Call for help reached none of the waiting test bots.
- **Multiplayer test helper:** `server/scripts/bot-adventurers.ts` (development only; refuses `NODE_ENV=production`) runs three bot players, each a normal account that signs up through the session challenge handshake, creates its avatar through `POST /avatar` with a real portrait and frame, and plays only through the web client's `/room` and `/session` endpoints. **Wanderbot** (Brakka, Rokur Warrior) always plays in its own room; **Watchbot** (Sylwen, Verdani Mage) waits on the welcome screen, answers Call for help and leaves when the caller leaves or the room ends; **Driftbot** (Kestra, Aevis Rogue) plays 7 rounds, then rests 5 minutes on the welcome screen, answering Call for help meanwhile. Separate accounts are needed because one account can be in only one room with one selected avatar. `BOT_FRIENDS=<names>` adds friends by name; `BOTS=<names>` runs a subset. Run with `cd server && BOT_FRIENDS=Babuni npx tsx scripts/bot-adventurers.ts`. In encounters every bot follows Babuni's simple rule: use an item if one solves it, otherwise a skill, otherwise roll the dice (system events always roll), choosing at random among several matches; availability comes from the web client's own `slotHasEnoughSolutionCharges`, with the content loaded from `/game-data/content`. Helpers also give up after 3 minutes without any change in the room (`HELP_STALE_MINUTES`), for callers who walked away before help arrived. Verified: Wanderbot kept its avatar look over three rounds; a simulated caller's Call for help brought Watchbot into the room, and Watchbot left when the caller left. A first version that wrote to the database directly lost its avatar look after a round and was replaced.
- **Verification:** `NODE_OPTIONS=--throw-deprecation npm run release:check` passed when the layout was first ported (9 client, 38 server tests); later server changes on this branch passed it with 39 server tests. ## 2026-11-10 — Test fix: random failures in `systemEventInventory.test.ts` and `roomService.test.ts`

- The level-up scenario in `server/src/services/systemEventInventory.test.ts` failed at random because it checked exact essence and spell counts while the encounters it used still granted randomly drawn rewards. A level-up's rewards are drawn when the encounter is created, from its own roll; a Prosperity draw can include an essence (seen in CI as 10 essence uses instead of 6). The normal encounter's random rewards could be an essence or spell 10001 itself (seen locally as 7 essence uses and as 3 charges of 10001 instead of 0).
- The test now gives that normal encounter no random rewards and removes essences from the pre-drawn level-up rewards. All assertions are unchanged. Game code is unchanged; granting an essence on a Prosperity level-up is existing behavior.
- `server/src/services/roomService.test.ts` (Continue past a disengaged participant) expected the next room state to be `active_encounter`, but it can legitimately be a level-up event (seen in CI on PR #22). It now accepts either state, as the file's other Continue checks already do, and also requires a new encounter snapshot. *Correction (2026-11-11): the original explanation here, that the next encounter is drawn at random and can be a system event, was wrong. A diagnostic run showed that in the failing case the avatar had already reached a new level in an earlier, random step of the test, and the owed level-up event is shown at the next opportunity, as designed.*
- **Verification:** `systemEventInventory.test.ts` passed 60 of 60 consecutive local runs (an earlier, partial fix failed 1 in 25); `roomService.test.ts` passed 30 of 30. Because the random cases are rare, these runs show the changes work but cannot prove every random path is covered. `NODE_OPTIONS=--throw-deprecation npm run release:check` passed (9 client, 38 server tests). Nobara, local Podman PostgreSQL.

## 2026-11-10 — Unreleased: one copy of the game content

- `server/game/*.json` is now the only copy of encounters, solutions, expansions, frames and portraits. The duplicate copies in `client/src/data/game` and `client/public/game` were removed; images stay in `client/public/game`.
- New public endpoint `GET /game-data/content` serves all content in one response with an ETag (`Cache-Control: no-cache`), so a returning browser gets `304 Not Modified` when nothing changed. The client loads it during the loading screen instead of building the JSON into the app; the main JavaScript bundle shrank from about 948 KB to 511 KB.
- The server re-reads a content file when its modification time changes (checked at most once per second) and keeps the last good copy if a file is invalid. Admin saves are written atomically. Content edits therefore reach players on their next page load, without a rebuild or restart. Running rooms keep their own encounter snapshots.
- `npm run verify:static-data` now checks the single source: structure, matching ids, references from encounters to solutions, follow-ups and expansions, image files, and that no client copy has been reintroduced.
