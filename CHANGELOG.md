- **Fix: Call for help skipped players with a paused solo adventure.** Leaving a solo adventure only pauses its room, and the player stays listed as its participant, so help invitations treated them as busy for good. This also stranded helpers: when a caller left, the helper was alone and its own leave only paused that room. A player now counts as busy only when their presence points at the room or the room is a party with someone else engaged (`isPlayerBusyInRoom` in `server/src/services/roomService.ts`). New test `server/src/services/helpInviteAvailability.test.ts` fails on the old rule and passes on the new one. Found while Babuni's Call for help reached none of the waiting test bots.
- **Multiplayer test helper:** `server/scripts/dev-bot-adventurer.ts` (development only; refuses `NODE_ENV=production`) runs three bot players, each a normal account that signs up through the session challenge handshake, creates its avatar through `POST /avatar` with a real portrait and frame, and plays only through the web client's `/room` and `/session` endpoints. **Wanderbot** (Brakka, Rokur Warrior) always plays in its own room; **Watchbot** (Sylwen, Verdani Mage) waits on the welcome screen, answers Call for help and leaves when the caller leaves or the room ends; **Driftbot** (Kestra, Aevis Rogue) plays 7 rounds, then rests 5 minutes on the welcome screen, answering Call for help meanwhile. Separate accounts are needed because one account can be in only one room with one selected avatar. `BOT_FRIENDS=<names>` adds friends by name; `BOTS=<names>` runs a subset. Run with `cd server && BOT_FRIENDS=Babuni npx tsx scripts/dev-bot-adventurer.ts`. In encounters every bot follows Babuni's simple rule: use an item if one solves it, otherwise a skill, otherwise roll the dice (system events always roll), choosing at random among several matches; availability comes from the web client's own `slotHasEnoughSolutionCharges`, with the content loaded from `/game-data/content`. Helpers also give up after 3 minutes without any change in the room (`HELP_STALE_MINUTES`), for callers who walked away before help arrived. Verified: Wanderbot kept its avatar look over three rounds; a simulated caller's Call for help brought Watchbot into the room, and Watchbot left when the caller left. A first version that wrote to the database directly lost its avatar look after a round and was replaced.

## 2026-11-10 — Test fix: random failures in `systemEventInventory.test.ts` and `roomService.test.ts`

- The level-up scenario in `server/src/services/systemEventInventory.test.ts` failed at random because it checked exact essence and spell counts while the encounters it used still granted randomly drawn rewards. A level-up's rewards are drawn when the encounter is created, from its own roll; a Prosperity draw can include an essence (seen in CI as 10 essence uses instead of 6). The normal encounter's random rewards could be an essence or spell 10001 itself (seen locally as 7 essence uses and as 3 charges of 10001 instead of 0).
- The test now gives that normal encounter no random rewards and removes essences from the pre-drawn level-up rewards. All assertions are unchanged. Game code is unchanged; granting an essence on a Prosperity level-up is existing behavior.
- `server/src/services/roomService.test.ts` (Continue past a disengaged participant) expected the next room state to be `active_encounter`, but the next encounter is drawn at random and can be a system event (seen in CI on PR #22). It now accepts either state, as the file's other Continue checks already do, and also requires a new encounter snapshot.
- **Verification:** `systemEventInventory.test.ts` passed 60 of 60 consecutive local runs (an earlier, partial fix failed 1 in 25); `roomService.test.ts` passed 30 of 30. Because the random cases are rare, these runs show the changes work but cannot prove every random path is covered. `NODE_OPTIONS=--throw-deprecation npm run release:check` passed (9 client, 38 server tests). Nobara, local Podman PostgreSQL.

## 2026-11-10 — Unreleased: one copy of the game content

- `server/game/*.json` is now the only copy of encounters, solutions, expansions, frames and portraits. The duplicate copies in `client/src/data/game` and `client/public/game` were removed; images stay in `client/public/game`.
- New public endpoint `GET /game-data/content` serves all content in one response with an ETag (`Cache-Control: no-cache`), so a returning browser gets `304 Not Modified` when nothing changed. The client loads it during the loading screen instead of building the JSON into the app; the main JavaScript bundle shrank from about 948 KB to 511 KB.
- The server re-reads a content file when its modification time changes (checked at most once per second) and keeps the last good copy if a file is invalid. Admin saves are written atomically. Content edits therefore reach players on their next page load, without a rebuild or restart. Running rooms keep their own encounter snapshots.
- `npm run verify:static-data` now checks the single source: structure, matching ids, references from encounters to solutions, follow-ups and expansions, image files, and that no client copy has been reintroduced.
- babuni.admin writes the JSON to `server/game` (separate change in that repository).
- **Verification:** see `docs/DEVLOG.md` (2026-11-10). **Not deployed.** Merged into `main` as PR #18 (`ee960792`) on 2026-11-10; deployed on 2026-11-11 (see above).
